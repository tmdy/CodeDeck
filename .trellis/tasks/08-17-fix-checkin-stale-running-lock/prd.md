# 修复签到状态残留与全局阻塞

## Goal

确保所有手动、批量和自动签到全局串行执行，并让应用重启后能够从中断的签到状态恢复，避免账号永久显示“签到中”并阻塞后续操作。

## Background

- 当前批量实现按站点分组，并通过最多 3 个 worker 并行执行不同站点：`electron/main.ts:2796-2820`。
- Renderer 会在任意账号为 `running` 或 `verifying` 时禁用全部签到入口：`src/App.tsx:784-787,4092`。
- 持久化状态恢复只将 `verifying` 转为 `manual_required`，但会原样保留 `running`：`src/shared/checkin/types.ts:106-136`。
- 用户明确要求所有账号全部串行，不保留跨站点并行。

## Requirements

- R1：手动单账号、手动批量和计划自动签到必须共享同一个全局串行执行边界；任意时刻最多执行一个账号的签到网络流程。
- R2：批量签到必须按输入账号顺序逐个执行，不再创建并行 worker，也不因站点不同而并行。
- R3：从持久化状态加载时，中断的 `running` 必须转换为可重试的失败状态，并提供明确的中断提示；不得继续占用全局运行锁。
- R4：中断的 `verifying` 继续恢复为 `manual_required`，保留现有“重新打开验证窗口”行为。
- R5：真实运行期间仍保持全局阻塞，避免用户启动第二个签到；任务结束或异常后必须写入终态并释放串行执行边界。
- R6：不改变签到鉴权、验证码验证、余额刷新和自动签到资格判断。

## Acceptance Criteria

- [ ] AC1：同时触发两个不同站点的签到时，第二个账号必须等第一个账号进入终态后才开始网络请求。
- [ ] AC2：批量签到不使用多个 worker，测试证明最大活跃签到数为 1，并保持输入顺序。
- [ ] AC3：持久化 `running` 状态在加载后变为 `failed`，提示上次签到中断且可以重新签到。
- [ ] AC4：持久化 `verifying` 状态仍恢复为 `manual_required`。
- [ ] AC5：单次签到抛错、登录失效、验证码要求或正常成功后，队列均继续处理下一项且不会留下永久 `running`。
- [ ] AC6：相关 Vitest 和 TypeScript 检查通过。

## Out of Scope

- 不改变账号自动签到开关、计划时间或批量汇总口径。
- 不修改站点 API 协议、验证码页面交互或浏览器会话安全边界。
- 不清除已经完成的成功、已签到、失败或人工验证结果。
