# 研究配置页首次打开缓慢

## Goal

解释 Profile 编辑页中“打开 Base URL”比“浏览器登录”更晚出现窗口的原因，并形成可验证的最小修复方案。用户价值是点击后立即获得窗口反馈，同时保留当前站点身份分区和安全导航约束。

## Background

- Profile 的 Base URL 打开和后台浏览器登录都走 Electron 内置 `BrowserWindow`，不是两个完全不同的浏览器实现。
- 当前“打开”路径创建隐藏窗口后等待 `loadURL()` 完成，随后才显示并聚焦窗口。
- 当前登录路径在等待初始导航前就显示并聚焦窗口；已有测试明确覆盖这一时序。
- “打开”动作的 renderer handler 直接等待 IPC，但没有独立的忙碌/加载反馈，因此隐藏窗口期间用户只能看到原配置页。
- 当前工作区已有未提交改动；本任务不得覆盖或重构无关改动。

## Requirements

1. 研究记录必须分别描述“打开 Base URL”和“浏览器登录”的 renderer、IPC、main-process 和 BrowserWindow 生命周期。
2. 研究记录必须区分“窗口可见时间”和“页面网络/文档加载完成时间”，不得把页面服务器延迟误报为窗口创建延迟。
3. 研究记录必须核对浏览器分区、缓存、导航限制、超时和父窗口差异，指出哪些是根因、哪些只是可能影响因素。
4. 形成一个不改变认证、分区归属或导航安全策略的最小修复方案；在用户明确批准最新规划摘要前，不修改产品代码。
5. 若后续实施，必须保留加载失败清理行为，并为打开路径提供与登录路径一致的可见反馈和有界导航等待。

## Acceptance Criteria

- [ ] 任务研究文件包含带文件/行号锚点的根因结论。
- [ ] 能明确解释为什么登录窗口较快可见，以及为什么“打开”会把网络慢伪装成窗口慢。
- [ ] 已记录当前代码没有实时“打开”耗时样本的限制，并说明如何在实施后验证。
- [ ] `design.md` 和 `implement.md` 给出最小改动边界、回滚点和窄范围验证命令。
- [ ] 本轮规划不修改 `src/`、`electron/` 产品代码，也不创建提交。

## Out of Scope

- 不更换 Electron 内置浏览器，不恢复系统默认浏览器打开。
- 不改变浏览器账号、持久分区、Cookie、认证协议或跨 origin 导航策略。
- 不优化目标站点自身首屏、代理、DNS 或网络质量；这些只能作为后续运行时测量项。
- 不处理与本次窗口可见时序无关的现有工作区问题。

## Open Questions

- None blocking planning. Implementation remains gated on explicit approval of the final planning summary.
