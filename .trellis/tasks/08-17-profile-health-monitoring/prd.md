# 实现 Profile 健康检测

## Goal

为 CodeDeck 的非官方 Profile 提供可验证的模型健康状态，使用户能区分网络/API 不可用、模型响应异常和上下文连续性丢失，而不是只依赖 HTTP 200 或模型列表接口。

## Background

- CodeDeck 保存 Profile 的 Base URL、活动渠道 Key 和所选模型，并由 Electron 主进程通过 Chromium 网络栈发起站点请求。
- CodeDeck 不代理外部 Claude Code / Codex CLI 的模型 HTTP 请求；被动健康信号只能来自受监控终端的结构化会话生命周期。
- 受监控终端已经能从 Claude/Codex 会话文件识别 `turn_completed`，系统直连终端没有等价的可靠事件。
- Profile 当前支持多渠道，因此主动探测状态必须绑定 Profile、活动渠道和所选模型，避免渠道切换后复用旧状态。

## Requirements

1. 为每个非官方 Profile 的当前活动渠道和所选模型维护本地健康状态，不把运行时探测结果写入可同步 Profile 配置。
2. 健康状态至少区分：可用、响应降级、限流、鉴权失败、模型不可用、网络错误和尚未检测。
3. 主动探测必须复用 CodeDeck 已有的受监控终端机制，以无窗口方式启动真实 Codex/Claude CLI；Electron 主进程不得直接向 Provider 模型 API 发送探测请求。
4. 第一次探测在真实 CLI 中创建专用健康会话并发送完整的中文“微型旅途札记”初始化提示；后续探测每次创建新的无头 CLI 会话，只注入固定规则、上一次 assistant 完整回复和本轮用户输入“继续”。
5. 每次探测在收到权威 `turn_completed` 后从本轮 Provider 会话 JSONL 读取最后一条 assistant 文本，并机器校验递增序号、上一轮承接词出现在正文、新承接词存在且变化；CLI 正常完成但校验失败应标记为降级。
6. 主动探测使用 Profile 当前活动渠道和“模型配置”中的当前模型构建正常 CLI 启动计划；请求协议、鉴权头、User-Agent 和网络行为全部由真实 CLI 负责。
7. 健康检测只保存上一次 assistant 回复和滚动校验状态；每轮完成后关闭无头 PTY，不保存或恢复历史 Provider 会话，确保每次请求上下文保持为固定规则加上一轮回复。
8. Codex 主动健康检测使用当前 Profile 工作目录下的专用 `CODEX_HOME`：`.codedeck/profile-health/codex-home`；检测会话 JSONL、专用配置和相关运行文件不得写入用户全局 `.codex`。普通 Codex 会话的存储位置保持不变。
9. 普通受监控终端产生可信 `turn_completed` 时，将启动时绑定的 Profile 目标标记为被动可用；直连终端不得伪造被动成功。
9. Profile 列表显示紧凑健康状态；Profile 信息区显示当前渠道的检测按钮、最近验证时间、延迟、来源、连续成功次数和最近失败原因。
10. 用户可以手动发起一次主动检测；自动主动检测默认关闭且首版不提供后台定时探测，同一目标不得并发重复检测。
11. 官方原生 Claude/Codex Profile 不执行主动检测，因为 CodeDeck 不持有确定的站点渠道和模型目标。
12. Profile、渠道、模型或鉴权信息变化后，旧健康滚动状态不得继续用于新目标。
13. 探测日志不得记录 API Key、Token、完整请求头或其他明文凭据。
14. 手动检测只允许已保存且与当前表单完全一致的 Profile；未保存或已修改草稿必须先保存，避免用临时凭据启动不可追踪的 CLI 会话。
15. 手动检测使用当前活动渠道和“模型配置”中的当前模型；不额外提供健康检测专用模型选择器。
16. Profile 信息区不再常驻显示“渠道名称”输入框；添加或重命名渠道时使用临时内联名称编辑器，释放出的右侧空间用于渠道健康检测。

## Acceptance Criteria

- [ ] 手动检测成功时，状态显示可用，并记录延迟、最近验证时间、主动来源和连续成功次数。
- [ ] 手动检测通过无窗口受监控终端启动真实 Codex/Claude CLI，模型请求不由 Electron `fetch` 直接发出。
- [ ] 第一次检测发送完整初始化提示；第二次检测创建新的无头 CLI 会话，输入只包含固定规则、上一次 assistant 回复和用户消息“继续”，不携带更早历史。
- [ ] Codex 健康检测的会话 JSONL 位于当前 Profile 工作目录的 `.codedeck/profile-health/codex-home/sessions` 下，不写入用户全局 `.codex`；普通 Codex 会话位置不变。
- [ ] CLI 完成但编号、承接词或状态格式不合法时，状态显示降级，而不是可用。
- [ ] CLI 启动失败、认证/限流/模型错误、超时和进程异常被映射为可区分的健康原因。
- [ ] 切换活动渠道或模型后不会展示或复用上一目标的滚动状态。
- [ ] 受监控终端的真实 `turn_completed` 能更新对应 Profile 的被动健康状态；直连启动不会产生该更新。
- [ ] Profile 列表和 Profile 信息区能显示健康状态，且不覆盖现有余额信息。
- [ ] 当前渠道行右侧提供手动检测入口，检测模型来自当前模型配置；不显示第二个模型选择器。
- [ ] 渠道名称只在添加或重命名时出现，已有渠道仍可重命名，且删除/切换行为保持兼容。
- [ ] 未保存或已修改草稿不能启动检测，并明确提示先保存；健康结果、上一次 assistant 回复和滚动校验状态能持久化并在重启后恢复。
- [ ] 官方原生 Profile 不显示可执行的主动检测入口。
- [ ] 本地状态加载能兼容没有健康字段的旧文件，保存/加载后健康状态不丢失。
- [ ] 单元测试覆盖状态标准化、响应解析与验证、错误分类、持久化迁移、被动事件映射和关键 UI 展示。
- [ ] `npm test` 与 `npm run typecheck` 通过。

## Out of Scope

- 通过终端文本关键字猜测系统直连终端是否成功。
- 绕过站点反自动化或禁止探测策略。
- 无限保存完整健康检测对话历史。
- 在首版中统计 token 成本、跨设备同步健康历史或提供全局站点监控大盘。
- 首版后台定时主动检测；当前仅支持用户手动触发，后续可在明确的站点策略设置下扩展。
- Electron 主进程直接调用 `/responses`、`/chat/completions` 或 `/messages` 进行模型探测。
